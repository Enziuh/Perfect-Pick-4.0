# Roster accuracy v1 — local implementation

## Decisions and contract

Owner's final clarification supersedes the strict all-week cutoff proposal. No
Week11 or other new deadline policy is introduced. Week9+ retains opening-game
kickoff minus one hour, other-game kickoff, equality eligible, protected on-time
entry/first-late precedence. Same established23-person roster is eligible since
Week1; absence never ends membership. No joins or withdrawals, per owner attestation.

The original scoring tables use completedGames as eligible submitted FINAL picks.
They are retained byte-for-byte for qualification, frozen-history comparisons and
legacy compatibility. New snapshot.accuracy is the versioned authoritative derived
representation: version ROSTER_FINAL_V1, fromWeek1, complete approved public roster,
and per-week FINAL game counts. It is generated by the server-side projector and
strictly reconciled to schedule/results and trusted aliases by the public contract.
It contains no new awarded points, outcomes, predictions or payments.

The shared tools/scoring/roster-accuracy.cjs projection applies those authoritative
period counts to roster rows. API and static adapters use the same module. Model
completedGames now means competition FINAL games; qualificationCompletedGames retains
the original count and totalPicks remains separate. All existing qualification,
champion, tiebreak, perfect-week and prize decisions are computed BEFORE derived
accuracy is applied and continue using the original records. Missing roster members
get zero points; existing rows keep their order, points and rank numbers. A rank
mismatch throws rather than silently changing a protected result.

## Activation and old payloads

New format is opt-in server-owned configuration only:
accuracyRules:'ROSTER_FINAL_V1', rosterFromWeek1:true. The legacy-provider requires
23 approved aliases and an exact23-key match to the actual normalized player registry.
Ambiguous, missing, extra or unapproved identities fail closed. No private config was
edited in this work. No request/browser flag can authorize membership or publication.
Legacy PP3 endpoints and scorer outputs remain unchanged.

New clients still accept old payloads with their original accuracy semantics. They
show the new Games Final description and accuracy notice only when the versioned
correction is present. This avoids claiming corrected historical data before the
source is upgraded. Older clients are expected to reject an unfamiliar optional
accuracy field: release compatible clients before activating source metadata.

No cached records, proofs, timestamps, cutoff grants, expiry windows or retention
policy are extended. Content comparison includes snapshot.accuracy, so first activation
is not skipped as unchanged content. Public ID remapping covers every roster member.
Static aggregateStandings remain frozen qualification/scoring evidence; the same
versioned projection derives displays from their period coverage. Running periods
use explicit coveredWeeks; they never invent points for undisclosed weeks. Privacy
withholding and missing-data states remain intact.

## Status and limitations

Only FINAL games count. Existing nonfinal/unknown/inconsistent-result handling is
preserved, including fail-closed unsupported source statuses; canceled/postponed games
do not become FINAL by elapsed time. No Results normalization or score-sync change.
Invalid candidate entries retain existing rejection behavior and earn no new points;
rostered players still receive the finalized-game denominator. Missing cutoff evidence
continues to withhold points/confirmation rather than guess timing.

Historical alias approvals/captures were checked locally:23 unique approved records,
consistent public alias sets. Current live registry is not independently verified;
the actual provider repeats the full registry check before opting in. No current
Google source, Form state, trigger execution or live API/static parity was claimed.
